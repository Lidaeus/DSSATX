## 2. 阻塞性发现

### P0-1：D1 的 split、stage 参数和规模配置没有被任何运行入口消费

四个 D1 文件已写入 `configs/runs/`，但代码中没有读取 `eggplant_p1_v4_design_20260717.json`、`eggplant_p1_v4_staged_params_20260717.json` 或 `xxql2501_v4_validation_split_20260717.json` 的实现。当前 `build_pest.py` 只可读取 observation policy 和 frozen bounds。

如果现在按旧命令构建：

- `bounds_id` 仍指向20 active 的旧 Sobol bounds，stage2 最终释放14个，而不是S1的2个或S2的4个；
- 所有10个处理继续以非零权重进入 Pst，TN5/TN13 不会成为独立 validation，TN9/TN14 也不会成为 diagnostic；
- 累计采收 `PWADM` 和增量采收 `PWAIM` 会同时进入 Phi。

因此“冻结设计”目前是被动文档，不是可执行契约。下一轮首要任务是让一个简单的 `--design-config --stage` 入口实际控制参数、处理角色、观测用途和权重，并输出构建审计表。

### P0-2：S4 用 validation 改善来筛参数会造成验证泄漏

staged config 当前要求 S4 参数“实际更新、无异常边界且改善 validation”。一旦用 TN5/TN13 的表现决定参数是否进入 S4，它们就参与了模型选择，不再是独立 validation。

必须改为：S4 survivor 只依据 calibration 集上的参数更新、边界、相关性、过程解释和确定性复跑选择；冻结 S4 后才首次计算 TN5/TN13 指标。若验证失败，报告局限，不把处理加回率定，也不据此反复选择参数。

### P0-3：自动 IES 门只实现了工程门，却写成 `validated`

`run_parallel._assess_completed_ies()` 调用的是现有 P0 通用 `assess_ies_run()`。该门检查初末集合、有限性、Phi差异、参数更新和成员保留，但没有检查：

- 每轮 realization 保留与剔除原因；
- 分组 Phi 和观测组支配；
- 参数边界堆积；
- calibration/validation 角色与指标；
- 代表 realization 的独立确定性复跑。

通用门一旦通过，runner 会直接写 `scientific_status=validated`，而异参同效入口又把该字符串作为上游科研通过。这会把“工程上非退化”误当“P2科学有效”。

必须拆成两个状态：`engineering_validated` 与 `science_validated`。只有完整 P2 finalize 后者才可为真；equifinality 和正式论文导出只接受后者。

### P0-4：results manifest 门仍可绕过，且 trajectory 未做逐文件哈希校验

正式导出时 `--results-manifest` 仍是可选参数；不传即可回到旧路径。传入后，trajectory 只要求其目录下“存在任意一个 manifest 成员”，并没有验证实际读取的 `PlantGro.OUT/FreshWt.OUT` 的逐文件哈希。当前也没有 results manifest 生成器或回归测试。

`scenario_type` 同样是调用者自报，R端没有按图族验证；input manifest、bounds、weights、validation split 哈希仍未写入 paper bundle。

必须改为：正式导出强制使用一个由 finalize 生成的 results manifest；导出器只读取该 manifest 注册的具体文件及哈希，不接受目录模糊匹配；scenario type 从上游 manifest 继承而非 CLI 任意指定。

## 3. 重要配置问题

### P1-1：sigma 主方案和稳健性对照混在同一个文件

`assumption_based_sigma_v1.csv` 已把 `PWAIM group_multiplier` 直接设为1.25，因此它不是“所有组等权”的主方案。要比较1.0与1.25，需要两个独立、哈希冻结的 policy：

- primary：所有组倍率1.0；
- contrast：仅 PWAIM 为1.25。

此外，explicit `sigma` 存在时，当前 policy 实现不会组合 `model_sigma/sigma_floor`，这些字段现在只是未使用说明，容易让用户误以为最终 sigma 已按平方和重算。

### P1-2：累计与增量采收仍会重复进入目标函数

policy 同时给 `PWADM` 和 `PWAIM` 非零权重。真实预检Pst中二者各有110项非零观测，会对同一采收过程重复计数。已批准设计要求增量采收进入 Phi、累计采收只做 diagnostic；这必须由构建器的 observation-use 过滤实现，不能只靠 sigma 表表达。

### P1-3：变量说明和处理水分标签存在错误

- `CNAMM` 的观测值约113–171，语义为冠层/地上部氮量类指标，不是“25% nitrogen content”；当前 sigma note/source 单位说明错误。
- validation split 的 rationale 把水分等级写反：权威 metadata 为 TN2–5=`W3`，TN10–13=`W1`，而 config 写成 TN2–4=`W1`、TN10–12=`W3`。

这些错误会直接进入方法描述和图例，必须在任何运行前更正并加契约测试。

### P1-4：审批范围需要明确为“工具开发配置”

用户在 P2 计划中的批注明确接受这些内容“作为工具开发阶段配置”。D1 JSON 当前只写通用 `approved_by`，容易被解释为正式科研参数和正式验证设计已冻结。建议增加 `approval_scope=tooling_development` 与 `science_use_status=pending_run_validation`；完成S1–S3工程验证后，再为正式S4创建独立ID。
