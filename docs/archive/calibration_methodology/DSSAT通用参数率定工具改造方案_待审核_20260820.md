# DSSAT 通用参数率定工具改造方案（待审核）

> 状态：方案待审核；本文不构成实施授权。  
> 日期：2026-08-20  
> 适用范围：将当前 DSSAT × PEST++ eggplant/TMGRO 专用工作流演进为支持多数 DSSAT 作物、CUL/ECO/SPE 参数和多种执行环境的易用工具。  
> 暂定代号：`DSSAT-Cal vNext`（仅用于方案讨论，不建议现在重命名仓库或命令）。

## 1. 结论先行

建议采用“**兼容层保留 + 描述符驱动内核 + 分级作物包 + 证据化支持声明**”的渐进式改造，而不是重写现有系统。

当前代码已经具备 TMGRO 场景下 CUL、ECO、SPE 注入、PEST++ IES、冻结边界、并行执行、结果追溯和论文数据冻结等重要能力。主要瓶颈是这些能力仍绑定于 `TMGRO048`、特定标签、固定模式和 eggplant 观测结构。通用化的核心应当是：

1. 把“生物学作物”“DSSAT 作物代码”“模型模块”“基因型文件 stem”“DSSAT 版本”拆成独立身份；
2. 用版本化参数描述符统一表达 CUL/ECO/SPE 中参数的位置、语义、作用域、格式和约束；
3. 将作物差异封装在可审查的 crop/model pack，而不是继续增加 `if mode == ...`；
4. 对每一种“支持的作物”给出 C0–C4 覆盖等级，避免把“能找到文件”误写为“可科学率定”；
5. 先稳定 CLI 和项目配置，再提供使用同一内核的本地 GUI；
6. 旧的 `eggplant_stage2` 等入口先作为兼容适配器保留，只有在新旧双轨结果等价后才退役。

GLUEP 值得借鉴的是统一控制文件、自动读取基因型上下界、并行执行、GUI/HPC 和多数作物适配；不应照搬的是对文件内 `!Calibration`/MINIMA/MAXIMA 标记的强依赖。GLUEP 的公开代码和说明主要覆盖 CUL 及可选 ECO，未找到其公开支持 SPE 率定的证据，因此 SPE 可以成为本工具的重要扩展点，但必须依靠严格的定位与回读验证，而不能只靠绝对行号。[GLUEP 论文](https://doi.org/10.1016/j.compag.2024.109513)、[GLUEP 源码](https://github.com/DSSAT/glue)、[GLUE 新作物说明](https://documentation.help/GLUE/adding__a_new_crop.htm)

## 2. 现状审计与改造边界

### 2.1 已有资产，应当保留

- `build_pest.py` 已能构建复杂 PEST 控制文件、多个观测组和阶段化率定任务；
- `run_dssat.py` 已形成“PEST 写参数 CSV → runner 注入 DSSAT 文件 → 运行 → 提取输出”的安全模式；
- 冻结 bounds、manifest/hash、工程与科研状态分离、stale-output 检查、独立 worker 目录和 `w = 1/sigma` 权重语义均具有较高复用价值；
- 当前 R-only 论文图管线和 `science_validated` 门禁应保持不变；通用化不应重新引入 Python 论文绘图实现；
- eggplant 通过 tomato 的 `TMGRO048`/CRGRO 模型运行这一事实必须继续显式记录，而不能把生物学作物名直接等同于 DSSAT 作物代码。

### 2.2 当前耦合点

- `build_pest.py`、`run_dssat.py` 和 `run_multiseason.py` 存在 `TMGRO048.CUL/ECO/SPE`、`CRGRO048`、特定 cultivar/ecotype 与标签的硬编码；
- `param_registry.py` 的物理边界与默认边界主要围绕现有作物建立；
- `parameter_modules.py` 虽已有参数模块、锚点和约束概念，但文件映射仍指向 TMGRO；
- CUL/ECO 的表头、MINIMA/MAXIMA 和 `!Calibration` 标记在 DSSAT 作物间并不统一，SPE 更是块状、非规则格式；
- 观测提取、变量命名、收获逻辑和误差模型仍与 eggplant 多收获场景紧密耦合；
- 单体构建器和 runner 体量较大，继续添加模式分支会增加回归风险。

### 2.3 本机 DSSAT v4.8 基因型语料快照

对 `C:\DSSAT48\Genotype` 的只读盘点显示：共有 56 个 CUL、56 个 SPE、51 个 ECO stem；51 个 stem 同时具有三类文件。CUL 中 51/56 有 MINIMA/MAXIMA 和 `!Calibration`，ECO 仅 27/51 有 MINIMA/MAXIMA、23/51 有 `!Calibration`。同时，CROPGRO、CERES、SUBSTOR、CANEGRO 等文件的字段布局差异明显。

这说明“文件存在”不等于“可以依靠统一标记自动率定”。通用工具必须同时支持：标准标记自动发现、作物包显式描述、版本指纹核验和人工确认。

### 2.4 明确不在首轮范围内

- 不开发新的优化算法；优先复用 PEST++ IES，并通过 adapter 预留其他后端；
- 不承诺一次性支持 DSSAT 的全部作物和全部输出变量；
- 不在通用内核稳定前开发云平台、多用户服务或复杂桌面 GUI；
- 不改变现有论文图的 R-only 规则；
- 不把未经独立验证的 eggplant 结果描述为普适作物模型结论；
- 不自动推断缺失的处理、灌溉、氮肥或变量语义；必须由显式元数据确认。

## 3. 目标与可验收定义

### 3.1 产品目标

用户只需完成四类输入即可建立任务：

1. 选择 DSSAT 安装、版本、模型和作物/基因型；
2. 指定试验文件与观测数据映射；
3. 从被发现的 CUL/ECO/SPE 参数中选择率定项、边界和层级；
4. 选择算法、预算、并行资源和验证拆分。

工具随后生成可审查计划，经过静态验证和 baseline smoke test 后才允许正式运行，并输出完整 provenance、参数集、预测区间、诊断和冻结的报告数据。

### 3.2 “支持某作物”的五级证据

| 等级 | 定义 | 必须通过的证据 | 可使用的对外表述 |
|---|---|---|---|
| C0 | 已发现 | 能识别作物、模型和文件组合 | “已识别” |
| C1 | 可解析 | 全量读取并无损 round-trip | “格式兼容” |
| C2 | 可安全修改 | lower/init/upper 注入、回读一致、仅目标字节变化 | “参数化支持” |
| C3 | 可执行 | baseline 与扰动 smoke test 成功，输出可提取 | “工程支持” |
| C4 | 经科学验证 | 真实多环境率定、留出验证、基准与复现包完成 | “科学验证支持” |

首个公开通用版本的建议门槛是：本机/发行版语料中至少 80% genotype stem 达到 C2；至少 6 个作物、4 个模型家族达到 C3；至少 4 个作物、3 个模型家族达到 C4。以上是建议目标，不是当前已达到状态。

## 4. 目标架构

```text
CLI / 本地向导 / 后续 GUI
          │
          ▼
项目规范 project.yaml ──► 可审查 calibration_plan
          │
          ▼
作物与模型目录 ──► crop/model pack ──► 参数描述符与约束
          │                         │
          │                         ├─ CUL codec
          │                         ├─ ECO codec
          │                         └─ SPE block codec
          ▼
观测 adapter ──► 目标函数/误差模型 ──► optimizer adapter
          │                                  │
          └──────── execution backend ◄─────┘
                         │
                         ▼
验证门禁 / provenance / 报告数据 / 现有 R 论文图管线
```

### 4.1 身份模型

建议将以下字段设为一等公民：

```yaml
biological_crop: eggplant
dssat_crop_code: TM
model_id: CRGRO048
genotype_stem: TMGRO048
dssat_version: 4.8.5
cultivar_id: TM0001
ecotype_id: TM0001
```

这样可正确表达“eggplant 使用 tomato 模型与文件”，也能处理同一作物多个模型版本、一个模型家族多个作物以及升级后的文件布局。

### 4.2 参数描述符

每个参数应至少包含：

- 稳定 ID、显示名、单位、科学含义和来源；
- `file_kind ∈ {CUL,ECO,SPE}` 与作用域 `cultivar/ecotype/species`；
- section anchor、实体 selector、表头/token 名或数字 token 索引；
- 预期相邻标签、字段宽度、精度、科学计数法规则和缺失值约定；
- 物理硬边界、建议先验、变换、参数组和跨参数约束；
- 支持的 DSSAT 版本范围、源文件指纹和兼容状态；
- 注入后的回读容差与不变量。

绝对行号只能作为 hash 锁定后的派生缓存或最后退路，不能成为公开作物包的主要定位方法。dpest 对 SPE 已采用“行号 + 数字列索引”的显式接口，证明 SPE 可纳入参数化，但也提示版本漂移风险；本方案应在此基础上增加锚点、上下文和文件指纹。[dpest SPE 文档](https://dpest.readthedocs.io/en/latest/dpest.spe.html)、[dpest JOSS 论文](https://doi.org/10.21105/joss.08188)

### 4.3 三类文件的层级语义

- **CUL**：通常是 cultivar-specific，适合基因型专属性状；
- **ECO**：通常由多个 cultivar 共享，修改会影响同 ecotype 的多个 cultivar；
- **SPE**：species/model-level，可能影响该物种模块的所有 cultivar 与 ecotype。

因此不能把三类参数简单放入一个平坦向量。工具必须显示影响范围，并在计划中列出“一个参数会改变哪些处理/季节/基因型”。SPE 参数原则上需要多 cultivar、多环境资料共同约束；只有单 cultivar 数据时，可估计的是该试验下的“有效参数”，不得直接宣称得到物种通用参数。

### 4.4 文件 codec 与安全写入

三个 codec 共享相同契约：

1. parse 为 typed document，保留原始文本、换行和字段 span；
2. resolve descriptor，若锚点、表头或实体不唯一则失败；
3. format 按字段宽度写入候选值；
4. parse-back，验证数值、约束和实体身份；
5. byte-diff containment，确认只有目标 span 变化；
6. 写入运行沙箱，绝不原地修改 DSSAT 安装目录或模板源文件。

这也要求继续沿用当前较安全的间接模板模式：PEST 只写统一参数文件，由 runner 负责 DSSAT 文件的精确注入与校验。

### 4.5 crop/model pack

每个 pack 建议包含：

```text
packs/<model_family>/<crop_code>/<version>/
  pack.yaml
  parameters/*.yaml
  observations.yaml
  constraints.yaml
  fixtures/
  compatibility.json
  README.md
```

pack 只描述差异，不包含优化器逻辑。每个 pack 必须记录维护者、数据来源、DSSAT 版本、许可、C0–C4 等级和最近验证日期。

### 4.6 观测与输出 adapter

把当前 phenology、growth、multi-harvest 和 joint 逻辑抽成统一长表契约：

```text
experiment, treatment, replicate, date/dap, variable,
observed, sigma, unit, role, source_file
```

每个输出 adapter 负责：DSSAT 输出文件、变量名/列、时间键、单位换算、缺失与多收获语义。变量映射必须来自 pack 或项目配置，不能根据处理号或列位置猜测。误差模型和权重属于项目层，而不是写死在作物逻辑中。

### 4.7 优化与执行 adapter

- 首选后端：PEST++ IES，保留当前并行 worker、失败检查和 ensemble 诊断；
- 兼容后端：PEST/GLM 可作为点估计或历史复现；
- 可选后端：GLUE 仅在研究比较或用户明确选择时启用；
- 执行环境统一为 local serial、local parallel、SLURM/HPC 三类 backend；
- 所有后端使用相同 calibration plan、观测表、参数边界和预算收据，避免结果不可比。

PEST++ IES 的优势是非侵入式、可并行且每轮模型调用主要随 ensemble size 而非参数数线性增长；但 ensemble 只能被解释为条件不确定性近似，不能自动称为严格贝叶斯后验。[PEST++ IES 官方说明](https://help.pesthomepage.org/pestpp-ies.html)、[PEST++ 源码](https://github.com/usgs/pestpp)、[White 2018](https://doi.org/10.1016/j.envsoft.2018.06.009)

### 4.8 易用性设计

建议先实现以下稳定命令，再做 GUI：

```text
dcal init       创建项目模板
dcal inspect    识别 DSSAT、作物、文件、参数与输出
dcal plan       生成不可变的 calibration plan
dcal validate   静态、格式、baseline 与扰动验证
dcal run        运行率定/验证
dcal status     查看并行与失败状态
dcal report     生成诊断和冻结报告数据
```

本地 GUI 只调用上述公共 API，不能另写科学逻辑。GUI 的关键交互应是参数作用域预览、边界审查、观测映射预览、计算预算估算和失败解释，而不仅是把 CSV 换成表单。

## 5. 配置与产物建议

### 5.1 单一项目入口

参考 GLUEP 的单一 `SimulationControl.csv` 思路，但使用有 schema 的 `project.yaml`，并允许从 CSV/向导导入：

```yaml
schema_version: 1
dssat:
  home: C:/DSSAT48
  version: 4.8.5
model:
  biological_crop: eggplant
  crop_code: TM
  model_id: CRGRO048
  genotype_stem: TMGRO048
data:
  experiments: [data/raw/experiments/...]
  observations: observations.csv
parameters:
  pack: crgro/tm/4.8
  selection: configs/parameters/eggplant_stage2.yaml
calibration:
  backend: pestpp-ies
  budget: {noptmax: 6, ensemble_size: 80, seeds: [101]}
validation:
  split_file: validation_split.csv
execution:
  backend: local_parallel
  workers: 6
```

自动发现的内容必须写入一个待确认的 plan；用户确认后锁定 hash，正式运行不能静默改变。

### 5.2 标准运行产物

- `calibration_plan.yaml`：所有解析后的身份、参数、边界、观测和预算；
- `compatibility_receipt.json`：pack、DSSAT、文件 hash 与覆盖等级；
- `parameter_impact.csv`：每个参数的层级和受影响实体；
- `observation_contract.csv`：变量、单位、时间键、sigma 与 role；
- `execution_receipt.json`：实际调用次数、失败数、CPU/墙钟时间、seed；
- `run_manifest.yaml` 与所有输入 hash；
- calibration/validation 的 frozen comparison 与 ensemble 数据；
- 工程状态与科研状态分开记录。

## 6. 渐进迁移路线与阶段门禁

### P0：冻结现有行为

交付物：

- 为当前 TMGRO CUL/ECO/SPE 注入、观测提取和 deterministic run 建立 golden fixtures；
- 建立 architecture decision records，明确身份模型、pack schema 与兼容策略；
- 记录现有命令输出、manifest 和关键 DSSAT 输出 hash/容差。

退出门禁：现有测试和基准可重复；未改变科学结果。

### P1：目录、schema 与语料测试

交付物：作物/模型 catalog、descriptor schema、`project.yaml` schema、全 genotype 语料盘点、C0/C1 报告。

退出门禁：56 个本机 CUL/SPE 和 51 个 ECO 均有机器可读兼容报告；不支持项有明确原因。

### P2：通用 CUL/ECO codec

交付物：typed parser、精确 formatter、round-trip、byte containment、MINIMA/MAXIMA/显式 descriptor 双通道。

退出门禁：选择的 CROPGRO、CERES、SUBSTOR 与一个异型格式家族通过 C2。

### P3：SPE codec 与层级参数图

交付物：section anchor、上下文指纹、token span、影响范围图、SPE 多实体安全检查。

退出门禁：至少三个模型家族的 SPE 参数在 lower/init/upper 上通过回读和扰动测试；版本错配能 fail closed。

### P4：观测、优化器和执行层解耦

交付物：统一观测契约、输出 adapter、optimizer adapter、local/HPC backend 接口。

退出门禁：当前 eggplant 旧入口与新 pack 在相同参数、seed 和数据下产生等价的补丁文件、模拟输出和目标函数。

### P5：首批 crop packs

建议首批选择：小麦 WHCER、玉米 MZCER、大豆 SBGRO、马铃薯 PTSUB，再增加水稻 RICER 和 tomato/eggplant TMGRO。这样既能与 GLUEP 案例对照，又覆盖不同模型家族和文件格式。

退出门禁：至少 6 作物/4 家族达到 C3；pack 文档、许可和维护责任明确。

### P6：易用性与发行工程

交付物：CLI 向导、错误解释、预算预估、resume、打包复现实验、后续本地 GUI 原型。

退出门禁：新用户可按文档从空目录完成 inspect→plan→validate→run；失败不会损坏模板或产生可误用的“成功”状态。

### P7：科学基准与公开发布

交付物：多作物基准、独立验证、对比/消融、版本化数据包、复现说明和论文数据。

退出门禁：达到预定 C4 覆盖；所有强主张有对应证据；论文图只从 `science_validated` 冻结数据生成。

## 7. 兼容与回归策略

1. 现有命令和 mode 暂不删除；内部逐个改为调用新 adapter；
2. 每迁移一个模式，都进行 old/new dual run，比较参数文件、目标函数、观测数量、模拟输出和 manifest；
3. 允许格式化的数值容差必须显式记录，不能用宽松整文件 hash 掩盖差异；
4. 新 pack 不得直接写入 `C:\DSSAT48\Genotype`，只在 run sandbox 中生成工作副本；
5. 冻结 bounds 生命周期继续作为唯一正式率定边界入口；
6. 已有 paper_data contract、R renderer 和 figure registry 保持独立，不随通用化重构。

## 8. 风险与控制

| 风险 | 后果 | 控制措施 |
|---|---|---|
| DSSAT 版本/文件漂移 | 写错参数或错误格式仍可运行 | 版本指纹、上下文锚点、回读、fail closed |
| SPE 层级误用 | 单作物/单 cultivar 过拟合并外推 | 影响范围展示、多层级数据门禁、声明限制 |
| 参数补偿与不可辨识 | 拟合好但参数无物理意义 | SA、先验、层级/阶段化率定、留出验证、边界率报告 |
| 输出变量语义不一致 | 跨作物指标不可比 | 版本化 observation adapter、单位审计、显式 variable role |
| GUI 过早 | 两套逻辑和高维护成本 | CLI/API 优先，GUI 仅调用公共内核 |
| “支持多数作物”夸大 | 科研与产品信誉风险 | C0–C4 能力矩阵和发布日期 |
| 基准工具版本漂移 | 对比不可复现 | 固定 release/commit、保留原始配置和环境收据 |
| 实验数据许可不清 | 无法公开复现 | 逐数据集许可审计；能公开的配置/合成数据单独发布 |

## 9. 审核时需要决定的事项

在任何实施前，建议项目负责人明确批准以下决策：

1. 是否接受“兼容适配器 + 新内核”的渐进方案，而不是大重写；
2. 首版支持声明采用 C0–C4 分级，且不把 C1/C2 写成科学验证支持；
3. 首批 crop packs 是否采用 WHCER、MZCER、SBGRO、PTSUB、RICER、TMGRO；
4. SPE 参数是否强制显示 species-level 影响范围并设置更高科学门禁；
5. 是否以 PEST++ IES 为首选优化后端、PEST/GLUE 为兼容/研究后端；
6. CLI/API 先行、GUI 后置的产品顺序；
7. 首个公开版本的 C2/C3/C4 数量门槛；
8. 是否允许在通用化期间继续推进 eggplant 科研率定，若允许，应保持工作目录和科学状态完全隔离。

## 10. 建议的批准方式

建议先只批准 **P0–P1 的设计与只读语料验证**，评审产物后再授权 P2。P0–P1 不应改变现有率定结果，也不应启动新的正式 DSSAT/PEST++ 科学运行。每个后续阶段单独提交变更清单、回滚方案和退出门禁，避免一次授权演变成不可控的大范围重构。
